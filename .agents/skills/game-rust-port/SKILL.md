# 原作を保つRust境界

通常は原作のゲーム本体を維持し、表示・入力・環境依存部分をRustへ分離する。ゲーム本体のRust化も明示された場合は、その範囲の規則移植と原作比較を別に扱う。対象作品の現在の仕様・ABI・移植範囲を使い、別作品の方式を機械的に適用しない。

## 着手と変更の検証

作業開始前に、要求された利用結果と保持条件をgoalへ設定する。既存のgoalがある場合は今回の要求と照合し、対象と完了条件を合わせてから着手する。

コード変更前に、変更する処理・依存先・共有契約から影響範囲と保持条件を定め、その範囲の期待する利用結果を確かめる回帰試験を選ぶ。不具合は再現条件を試験へ反映して先に失敗させ（Red）、必要な実装で通し（Green）、責務や重複を整理した後も同じ試験を通す（Refactor）。UIの実入力・実画面の確認は下の「実行による確認」に従う。

テストと検証は変更とその影響範囲に限定する。無関係な全試験・全端末・全コマンドの再実施を一律の条件にせず、過去の見落としだけを理由に全体へ広げない。追加の変更、試験の失敗、共有契約への影響、具体的な未解決リスク、ユーザー指定を根拠に追加確認が必要な場合だけ、理由を示して範囲を広げる。通過した範囲は新しい根拠がなければ繰り返さず、必要なビルドと配信される生成物の確認へ進む。

## 原作から責務を決める

原作の版・取得元・固定ソース、変更用ソース、実際に動く生成物を照合する。開始、コマンドと追加入力、描画、乱数、ターン、保存、終了を辿り、状態の所有者と比較可能な原作実行を確かめる。不具合では物理入力から状態遷移と表示まで症状を再現し、二重送信、入力待ち、表示キャッシュ、ゲーム処理を切り分けてから変更する。

変更前に、要求を現在の実装・表示と照合し、変更する対象と維持する対象を明示する。特定の端末・画面・文言の修正を、他の端末・画面・文言へ広げない。共有処理を変える必要がある場合は維持対象への影響を確認し、変更対象と維持対象に合わせて検証範囲を決める。

| 境界 | 所有するもの |
| --- | --- |
| 原作本体 | 移動、戦闘、生成、効果、ターン、RNG、知識・可視性、勝敗、原作serializer |
| Rust入力 | キー・タッチの意図、現在の入力待ちに従う変換、文字編集と後続選択 |
| Rust表示 | 公開済み観測、意味IDと翻訳、地図・HUD・ログ・メニュー・設定の構成 |
| Rust環境境界 | session寿命、保存コンテナの検査、永続化・import/export・復元の調整 |
| 接続部 | FFI、WASMメモリー、OS／ブラウザーAPIとイベントの観測 |

基本の経路は `操作部品 → Rust入力 → 原作本体 → Rust表示`。変更前に、PC・スマホ間および作品間の操作・表示・処理について、意味、更新契機、割込・停止・終端を整理し、共通化する範囲と分離する理由・境界を明記して設計する。同じ意味の操作・状態・停止条件は、状態と遷移の正本を一か所に置き、ボタン・タッチ・キーボードで反復の開始・周期、入力受付待ち、停止の判断を共有する。実行可否、対象選択、確定・取消の状態遷移と副作用も、共通意図の実行部で判断する。画面幅による配置、入力手段、作品固有の規則を混同せず、その反復・停止処理で入力方法ごとに分けるのは物理イベントの取得と共通意図への変換とし、反復タイマーや停止規則を重複実装しない。

状態は、冒険をまたぐ設定、冒険ごとに初期化する状態、一時的な操作状態に分類する。変更前に、新規開始・つづきから・終了それぞれで保持・初期化・復元・破棄する対象とタイミング、状態の所有者を決める。保存と結び付く状態は同じ冒険への対応を保ち、開始・復元の失敗や古い非同期応答で別冒険の状態を適用しない。

JavaScriptやOS接続はAPI実行と転送を担い、コマンドの意味、候補、可視性、保存妥当性を重複実装しない。入口だけのRustラッパーで完了とせず、判断と状態が実際にどこに残ったか確認する。

Bevyを使う作品ではsystem順序をこの契約へ合わせ、描画フレームや経過時間でターンを進めない。他作品へ同じECSやレンダラーを強制しない。

## 境界で失わせない情報

ABIは正本を一つにし、固定幅値、意味ID、型付き引数、長さ付きbytes等を渡す。借用寿命、確保・解放、版と失敗処理を明確にし、unsafeを接続部に限定する。

通常コマンド、品物、方向、文字、一覧・More、確認等の待ちを区別する。空queueをEscや仮入力にしない。原作が要求する後続選択を操作部品へ接続し、完了・取消後の次操作まで通す。方向選択は作品の通常方向入力を再利用し、一時操作は必要な待ちの間だけ出す。

操作ボタンとコマンドリストは必ず対応させ、どちらか一方だけにしない。PC・スマホとも、状況別ボタンやメニュー、条件付きで現れる操作を含め、対応する項目とボタンの操作内容・実行条件を一致させる。一覧から実行できる場合は同じ処理を使う。キーがある場合は一覧・ボタンの表示と実入力を一致させる。追加・変更・撤去時はボタンから一覧、一覧からボタンの両方向を照合し、片方だけ残さない。対応は状況別のUIも含めて扱い、全原作コマンドを画面下部へ常時並べる要件とはしない。

意味テキストは可能な限り整形前のsource-ownedなIDと引数で渡す。原作が一度選んだ公開名・外見・乱数結果を捕捉し、完成英文の逆解析や描画時の名前再生成に置き換えない。元のfilter、履歴、音声、callback順序も保つ。自由なユーザー文字列はデータである。

未公開地形、隠れた敵、罠、未識別の正体・効果・呪い等を、descriptor、翻訳引数、画像やラベルから公開しない。Canvas指定なら可視画面をCanvasへ出し、IME等の要素は必要なAPI接続に限定する。移植に未依頼の読み上げ等を混ぜない。

## 状態・乱数・保存を比較する

再描画、言語・倍率変更、スクロール、全画面切替だけで本体コマンド、RNG、更新を呼ばない。原作コマンド自身が消費する表示乱数とは区別する。固定seedと同じ消費済み入力を使い、状態・ターン・RNG・次の結果を原作と照合する。見た目や単一の終点だけで不変と判定しない。

原作serializerを保つ。外側の保存形式は必要な版・出典・ABI・bounds・整合検査を持ち、raw pointerや呼出しスタックを保存しない。入力途中の復元が必要なら、作品のcheckpointと実際に消費されたjournalを扱う。送信済み入力や物理キーを復元時に二重変換しない。

新instanceで検証・ロードし、待ちの再構築と次の原作操作を確認する。旧instanceのcallback・入力・catalog handleを新sessionへ渡さない。コンテナの検証成功と原作の復元成功を分ける。

## 実行による確認

既存のビルド・原作比較・実ブラウザー検証から、定めた影響範囲を確かめるものを選ぶ。変更した入力経路は、影響する後続選択・取消・表示・次操作まで実行する。UI変更は影響する利用サイズ・状態の画面を比較する。保存・入力・UIだけの変更でも、状態・ターン・RNGの保持条件に影響する経路は確認する。

全コマンド確認が依頼範囲なら、原作定義と条件付き経路から一覧を作る。未到達・skip・実機未確認を区別し、Rust単体の成功を原作実行の成功へ言い換えない。fixtureや操作用exportを通常配布へ混ぜない。

対象の入口は [親AGENTS](../../../AGENTS.md) と [作品一覧](../../../README.md)。作品内のAGENTSから現在のABI・原作仕様・検証手順を選ぶ。独立cloneに親や別作品のソースを実行条件として追加しない。
